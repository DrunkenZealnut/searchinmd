# pdf-keyword-highlight — 정본 출현 키워드를 원본 PDF 에 등급별 형광펜으로 표시

- 작성 2026-09-26 · 연구 책임자 결정: 교과서 스캔본은 Apple Vision OCR (D1), 색은 노랑·주황·초록 (D2)
- 입력 정본: `data/semantic_keyword_recount_20260917.xlsx` (2026-09-17 정본 실행이 `--xlsx-out` 으로 쓴 파일, `semantic_summary.json` `meta.run` 과 행 수·등급 분포 일치: NCS 11,517 = 3,788/5,227/2,502, 교과서 1,207 = 633/459/115)
- 산출물: `data/highlighted/` (비추적) — NCS 86권 + 교과서 9권 PDF 사본, 로그 JSON, 미발견 CSV, README(범례)

## 1. 왜 두 경로인가

| 말뭉치 | PDF 텍스트 층 | 글자 좌표 출처 | 표본 검증 |
|---|---|---|---|
| NCS 86권 (`data/markdown/ncs/pdf/<분야>/`) | 있음 (`pdftext`) | PyMuPDF `rawdict` | 600건 중 578 그 쪽 · 16 ±1쪽 · 6 미발견 |
| 교과서 9권 (`data/markdown/school-text/전공교과서(pdf)/`) | **없음** — 스캔본, 쪽당 이미지 1장, 글꼴 0 (변환기 OCR `surya`) | Apple Vision `VNRecognizeTextRequest` (ko-KR+en-US, accurate, 200 dpi) 글자 단위 `boundingBox(for:)` | 2쪽 프로토타입: 73건 중 71 발견, 쪽당 ~1.5 s |

교과서 13개 파일 중 『반도체산업의유해인자(에피스테메)』 4개는 같은 파일의 중복이고 마크다운·정본에 없으므로 대상이 아니다. 정본의 교과서 9권이 대상이다(`daegu/` 아래 『반도체공정기초(렛유인)』 포함).

## 2. 자료 흐름

1. **xlsx 읽기** — `NCS_매칭상세`·`교과서_매칭상세` (파일·키워드·등록 표현·실제 매칭·계층·줄·페이지·문맥·통일 등급·등급명). 행 순서 = 정본 엔진의 출력 순서(같은 줄 안에서는 매칭 시작 위치 순).
2. **줄 안 위치 재현** — xlsx 는 매칭의 줄 안 오프셋을 싣지 않는다. 정본과 같은 규칙 객체(`read_keyword_workbook` → `build_default_rules(keywords, "v2")`)와 `split_pages` 로 마크다운을 다시 훑어 `scan_document` 의 포함 판정(제외·보류·동반어)을 그대로 재현해 `(start, end)` 를 얻는다(`locate_included`). 각 (파일, 줄) 의 포함 매칭 순서열이 xlsx 행의 (키워드, 실제 매칭) 순서열과 다르면 그 줄은 **naive 대체**(대소문자 무시 k번째 인스턴스)로 내려가고 로그에 센다.
3. **쪽 글자 스트림** — 쪽의 글자를 추출 순서대로 `(문자, bbox, 줄 id)` 로 늘어놓고 `resegment._STRIP` 과 같은 정규화(NFC, 공백·마크다운 기호·문장부호 제거, casefold)를 글자별로 적용해 정규화 문자열 ↔ 글자 bbox 대응을 만든다. NCS 는 `rawdict`, 교과서는 Vision OCR JSON(쪽별 캐시 `data/highlighted/.cache/ocr/`).
4. **문맥 창 검색** — 마크다운 줄에서 매칭 앞·뒤 K자(정규화, K = 10 → 6 → 3 → 0)를 붙인 창을 쪽 문자열에서 찾는다. 유일 적중이면 확정. 여러 개면 같은 쪽에서 이미 쓴 구간을 제외하고 첫 번째(읽기 순서 ≈ 마크다운 줄 순서). 없으면 K 를 줄인다. K = 0 까지 없으면 **±1쪽**에서 같은 절차(정본의 줄→쪽 대응은 ±1쪽 정확도 94.9%). 그래도 없으면 미발견 CSV.
5. **형광펜 주석** — 매칭 글자 범위의 bbox 를 줄별로 합쳐 quad 로 만들고 `add_highlight_annot`. 색은 등급별(아래). 팝업 제목 `키워드 · 등급N 등급명`, 내용에 등록 표현·실제 매칭·정본 쪽(±1쪽으로 옮긴 경우 "정본 쪽 N, 표시 쪽 M"). 1쪽에 범례 주석 1개.
6. **저장** — 원본을 사본으로 복사한 뒤 사본을 열어 주석만 추가하고 증분 저장(`incremental=True`, `PDF_ENCRYPT_KEEP`). 원본 바이트는 건드리지 않는다. 회전된 쪽은 `derotation_matrix` 로 좌표를 되돌린다.

## 3. 등급별 색 (D2)

| 등급 | 뜻 | 색 |
|:---:|---|---|

## 5. 실패 처리

- PDF 대응 실패(LM 코드 없음 / 교과서 이름 불일치) → 실행 중단(정본 95권을 다 만들지 못하면 산출물이 아니다).
- `페이지` 가 PDF 쪽수 초과 → 미발견으로 기록.
- Vision 실패(빌드 실패·OCR 오류) → 해당 권 중단, 나머지 계속, 로그에 기록.
- 합계 불일치(처리 행 ≠ 12,724) → 종료 코드 1.

## 9. 구현 중 결정 (2026-09-26 — 연구 책임자 채택, 2026-09-26)

> **채택 (연구 책임자, 2026-09-26):** ① 중복 자리 원인 진단(§9-6)과 배치 정책 재조정(§9-2·7) ② 재탐색 — 먼 쪽(§9-8)·정본 쪽 OCR 대체(§9-9)·이웃 쪽 겹쳐 표시(§9-10). §10 의 최종 결과가 산출물의 기준이다. "재검산 규칙의 표 중복 문제"는 §9-11 의 검증으로 **철회**. ③ **그림·스크린샷 속 글자는 출현으로 센다** (연구 책임자, 2026-09-26 "그림 속 글자 포함") — 변환기가 OCR 해 본문처럼 넣은 문장(≈140건·1.2%)을 정본이 셌고 그대로 둔다. 정본 수치는 바뀌지 않는다(그 출현은 이미 11,517·1,207 안에 있다); 바뀌는 것은 형광펜 도구뿐이다 — 그림 속 글자를 텍스트 층 밖의 정당한 자리로 보고 이웃 쪽·먼 쪽까지 OCR 로 찾는다(§9-12).

시험 실행(NCS 『반도체 장비 안전관리』 1,631건 + 『반도체기초기술1』 47건)에서 드러난 사실과 그에 따른 변경:

1. **xlsx 는 같은 줄의 행을 (키워드, 실제 매칭) 정렬로 쓴다.** 엔진은 규칙 순서로 내므로 §2-2 의 "순서열 일치" 조건은 15% 의 줄에서 어긋났다(내용은 같고 순서만 다름). `assign_offsets` 는 **다중집합이 같으면** (키워드, 실제 매칭)별 큐로 문서 순서대로 대응한다. 결과: 두 권 모두 naive 대체 0줄.
2. **정본 출현 수 > PDF 본문 표현 수인 쪽이 많다**(안전관리 교재 84쪽에서 520건 초과 — 표·병합 셀 중복이 마크다운에 같은 셀 내용을 되풀이한 탓으로 보인다). §2-4 대로라면 소진된 행이 이웃 쪽으로 밀려 ±1쪽이 32% 가 됐고, 그중 절반은 정본 쪽에 표현이 있는 행이었다. 정본이 그 쪽이라고 말하는 출현을 인스턴스 부족을 이유로 옮기는 것은 데이터 왜곡이므로 **정책 변경**: 정본 쪽의 안 쓴 자리 → (표현이 그 쪽에 있으면) 이미 쓴 자리에 겹쳐 표시(`shared`, 팝업에 "같은 자리 중복 표시" 명기, 로그·README 에 별도 집계) → 표현이 그 쪽에 **아예 없을 때만** ±1쪽 → 미발견. 시험 실행 결과 안전관리 교재: 자기 자리 1,083 · 중복 자리 248 · ±1쪽 255 · 미발견 45(2.8%).
3. **문맥 창 사다리**: 양쪽 10/6/3자 → 뒤쪽만 → 앞쪽만 → 표현만. 표 셀 경계에서는 한쪽 문맥만 PDF 읽기 순서와 이어지기 때문. 로그의 `k` 는 시도한 창 크기가 아니라 **실제로 함께 맞춘 문맥 글자 수**다(0 = 표현만으로 배정 — 같은 표현이 여럿이면 순서 배정).
4. 범례 FreeText 는 테두리 색 없이(PyMuPDF 1.27 은 rich_text 없이 `border_color` 를 거부).
5. 시험 41개 (`test_highlight_pdf_occurrences.py`), CI 밖(pymupdf 필요).

미결(연구 책임자): 없음 — 그림·스크린샷 속 글자는 채택 메모 ③ 으로 종결. ±1쪽 표시와 남은 미발견은 `resegment.py` 줄→쪽 대응(앞부속의 이미지 전용 쪽에서 3~5쪽 어긋남)·OCR 오인식의 한계.

6. **연구 책임자 질문(2026-09-26, "왜 중복이 생겼나 / 재탐색")에 대한 진단** — 1차 실행의 중복 529건을 문맥 6자 이상 적중으로 분류: **A 이웃 쪽(±1)에 문맥 있음 199건(37.6%)** = 줄→쪽 대응이 한 쪽 어긋난 행이 정본 쪽의 자리를 다 써서 생긴 중복; **B 정본 쪽에 문맥까지 있음 257건(48.6%)** = 같은 문장의 사본이 정본 쪽에 있으나 자리가 소진된 행 — **정정(2026-09-26, §9-11)**: 처음엔 "마크다운이 PDF 보다 같은 내용을 더 담은 변환기 중복"으로 해석했으나, 책 전체 기준 문장별 사본 수를 비교하면 마크다운 사본 > PDF 사본인 문장은 NCS 전체에서 1문장(2건)뿐이다. B 는 PDF 에도 실제로 반복 인쇄된 문장(자기 평가·체크리스트 같은 반복 평가표)의 사본들을 줄→쪽 대응이 한 쪽에 몰아넣은 것이고, 정본 집계는 맞다; **C 어디에도 문맥 없음 73건(13.8%)** = PDF 텍스트 층·OCR 에 없는 글자(그림 속 글자·표 재배열). 미발견 213건은 NCS 전 쪽·교과서 ±12쪽을 문맥 8자 이상으로 재탐색하면 22건이 ±2~10쪽에서 **유일하게** 찾히고(11쪽 이상 적중 0), 191건은 책 어디에도 문맥이 없다.
7. **정책 재조정** (진단 A 유형 199건): 정본 쪽 자리가 소진됐을 때 이웃 쪽에 문맥 6자 이상(`NEIGHBOR_MIN_CONTEXT`) 적중이 있으면 중복 표시보다 그쪽을 우선한다 — 그 행의 문장이 실제로 거기 있다는 근거가 정본 쪽 라벨보다 강하다. 문맥 근거가 없는 소진 행만 정본 쪽에 겹쳐 표시.

10. **이웃 쪽 중복 표시(최후 수단)**: 정본 쪽에 표현이 없고 이웃 쪽의 표현 자리가 모두 소진된 행(36건)은 이웃 쪽에 겹쳐 표시하고 팝업에 두 사유를 함께 적는다. 미발견으로 두는 것보다 마크다운 중복(§9-6 B)의 같은 성격이라 판단.

11. **"재검산 규칙의 표 중복 문제" 검증 — 철회 (2026-09-26, 연구 책임자 예시 요청에 답하며)**: 책 전체에서 정본 행이 나온 문장(정규화, 12자 이상)마다 마크다운 사본 수와 PDF 텍스트 층 사본 수를 비교하면 마크다운 > PDF 인 문장은 NCS 전체에서 **1문장(『메모리 반도체 제조 공정 개발』, 같은 문장 2회 → 초과 2건)**뿐이고, 인접 표 행의 같은 열에 같은 셀 텍스트가 반복된 행 28건(위험성 평가표의 "화학물질의 노출 수준" 등)도 PDF 에 행마다 인쇄된 것이다. 즉 병합 셀·중복 줄로 정본이 부풀려졌다는 해석은 틀렸고, §9-6 B 는 반복 평가표의 사본을 줄→쪽 대응이 한 쪽에 몰아넣은 결과다(예: 『반도체 재료 품질관리』 113–114쪽, 같은 평가 문장이 PDF 두 쪽에 4회, 마크다운은 5회를 114쪽으로). 진짜 남는 쟁점은 **PDF 텍스트 층에 없는 글자를 변환기가 OCR 해 본문처럼 넣은 문장**: ±6줄 안에 그림·스크린샷 표시가 있는 행 142건(예: 『반도체용 세정 공정 재료 제조』 46쪽 안전보건공단 MSDS 검색 화면 스크린샷 → 표로 변환돼 MSDS 10건, 화학물질 다수), 도구의 미발견 98 + OCR 대체 46 = 144건과 같은 규모(≈1.2%). 이를 출현으로 셀지는 연구 판단.

12. **그림 속 글자를 이웃 쪽·먼 쪽까지 OCR 로 (2026-09-26, 연구 책임자 "그림 속 글자 포함" 이후)**: 미발견 98건을 정본 쪽·±1쪽·±2~10쪽 전부 Vision OCR 로 다시 읽어 분류하면 — **±1쪽 OCR 문맥 6자 이상 10건**, **±2~10쪽 OCR 문맥 8자 이상 38건**(개발·장비 분야 29권의 앞부속 "NCS 학습모듈의 내용 체계" 표 — 수행 내용 항목 "안전·유의 사항" — 가 이미지 전용 쪽이라 텍스트 층이 비었고, 줄→쪽 대응은 그 구간에서 3쪽 어긋난다: 정본 10쪽, 실제 7쪽, 문맥 12자; 『CMP 슬러리 재료 제조』 63쪽 표 8건 → 65쪽, 문맥 10~20자; 『반도체기초기술2』 소음 118 → 112쪽, 문맥 20자), **±1쪽 OCR 표현만(문맥 6자 미만) 29건**, 어디에도 없음 21건(OCR 오인식 `Fire`·`Radiation`·`X-선`, 텍스트 층에도 OCR 에도 없는 행). 정책: 텍스트 층 사다리와 대칭으로 OCR 사다리를 둔다 — 정본 쪽 OCR 6자+ → **±1쪽 OCR 6자+** → 먼 쪽 텍스트 8자+ → **±2~10쪽 OCR 8자+**(`FAR_OCR_MAX_PAGES`, `far`+`ocr`) → 정본 쪽 OCR 표현만 → 이웃 쪽 겹쳐 표시. **정본 쪽이 아닌 쪽에 문맥 없이 OCR 로 놓는 단계는 두지 않는다**: 위 29건의 절반(14건)은 개발·재료 분야 7권의 앞부속 예시 그림(네일숍 모듈의 "네일 샵 위생 서비스", 정본 10쪽·실제 5쪽) 인데, 이웃 9쪽의 다른 예시 그림에 "위생가운" 이 있어 그쪽을 잡는다 — 틀린 자리에 놓느니 미발견으로 남긴다.
